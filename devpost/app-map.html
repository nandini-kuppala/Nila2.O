Nila — app map

A take-home guide to the code: what the pieces are, where one action travels, and where to start a change. A snapshot of the code at the commit that added it; the code can drift after that.

The app in one paragraph

Nila is one static web page that behaves like a phone app. The ear turns sound into "how much of the last three seconds was crying". The ladder decides what happens next (play a sound, judge it, wake a parent). The engine does the audio, and the screens draw it. Everything Nila remembers lives in the browser's IndexedDB on the device. Watch, Babyproof, Ask, Doctor and Health are separate screens built around the same store.

One action: a demo cry, end to end

A synthesized cry plays into the same analyser a microphone would feed. Each tick the ear scores the sound, the ladder turns that into actions, the engine carries them out, and the screen redraws. When the episode closes, it is saved and the Timeline reads it back.

A route through the code (reference route)

  1. Where the press goes in. js/screens/monitor.js, search chooseDemo: the sheet's buttons call engine.startDemo('settles'). In js/monitor/audio-engine.js, startDemo wires the demo cry into the analyser, and begin starts the 50 ms loop.
  2. Where the decision is made. js/monitor/ladder.js, createLadder → tick. Rung by rung: quiet for 10 s closes the episode; a sound's turn ends with judgeSound (before vs. last 15 s, 60% drop = helped); 1:30 wakes; 0:20 plays the first sound from chooseSound. This file has no audio or screen code, which is why tests/ladder.test.mjs can drive it directly.
  3. Where it becomes visible and remembered. Back in audio-engine.js, handle plays sounds, records each verdict with store.recordSoundResult, and finish saves the episode with store.addEvent. monitor.js redraws the ladder (renderStatus) and the rows (renderTried); js/screens/timeline.js shows it the next morning.

A practice to reuse

Put the decision in a pure function, and test it with a scripted night. The ladder never touches audio or the screen; it is fed numbers and the time and answers with actions. That is what let tests/ladder.test.mjs catch two real bugs before the browser did. One was a sound still playing at the wake rung that was never judged (at 3× demo speed its turn ended a few milliseconds late). The other was a sound marked "helped" that was followed by hard crying. Both are now regression tests (see devpost/checklist.md → Revisions).

On the next project: when a feature has a clock and a judgement in it, write the judgement as a function of (readings, time) first, and drive it with a scripted scenario before wiring any device API to it.

Run it again

npm start, then open http://localhost:5173. Tests: npm test. No install step, Node 18+.
